Khatere API console

Runs every endpoint built so far — auth, user profiles, interests, host, moderator, circle, activity catalog + moderation, hangout planning, meetup pin, comments + voting, AI comment summaries, attendance + badges, and personalized recommendations — against a live API and shows the real request path and response for each step. The panel on the right always shows the exact JSON request each test sends, in run order, so you can scroll back and compare any two tests.

Batch 0 — Foundations

Health check, registration, login, refresh tokens, user profiles and interests, host and moderator accounts.

Batch 1 — Circle

Connection requests, accept/decline, blocks, and severing — including the guards and the block-deletes-connection database trigger.

Batch 2 — Activity catalog + moderation

Create activities as a user, a host, and a moderator; check that only approved activities are public; check that only moderators can see the queue or approve/reject; and check that a reviewed activity can't be reviewed twice.

Batch 3 — Hangouts

Create a hangout, invite participants, accept/reject, list by tab, chat, and cancel.

Batch 4 — Meetup Pin

Propose a time and place on a fresh hangout, confirm as a participant, change the pin and check every confirmation resets to pending, and check the guard rails (wrong user, no pin yet, hangout already cancelled).

Batch 5 — Archive

List and get archives from the now-cancelled Batch 3 hangout, upload media (photo/video validation), access control, personal delete, and the unanimous-purge flow.

Batch 6 — Ratings, Comments & Voting

Build a fresh completed, activity-linked hangout so A and B count as attendees. Rate the activity (attendee-only, 0.5-step validation, re-rating updates the average). Post comments as any user (moderation-gated, empty-body rejected). Approve/reject through the moderator queue. Vote comments up/down and check the 70%-of-votes ranking score updates and re-voting replaces the old vote.

Batch 7 — AI Comment Summary (DeepSeek)

Confirms the summary starts unavailable, stays unavailable while comments are only pending, and is generated (then regenerated) automatically each time a moderator approves a comment. A step failing at "after one approval" or "after two approvals" most likely means DEEPSEEK_API_KEY isn't set on this server, rather than a logic bug — check the container logs for the "AI comment summaries are disabled" line.

Batch 8 — Attendance Verification & Badges

Set up and read a host activity QR code, verify host-only access, create and read the one badge for the activity, scan the QR as a user, confirm repeated scans are idempotent, and check the caller's earned badge snapshots.

Batch 9 — Recommendations

Reads A's ranked suggestion feed. Checks the auth guard, the shape of each score (Total plus all five signals in [0,1], including SuggestionAcceptance), that the approved host activity from Batch 2 shows up, that InterestMatch is neutral for that still-untagged activity, that a forced refresh reflects the acceptance Batch 6 already recorded, that the limit param is honored, and that a second call reads the cache instead of recomputing.

Batch 10 — Activity Interests

Tags the approved host activity from Batch 2 with interests, confirms only the creator or a moderator can do that, confirms re-tagging fully replaces the old set, and closes the loop from Batch 9 by showing InterestMatch stop being the neutral 0.5 fallback once a user's own interests overlap with the tags. B's own interests are set here for the first time, purely so B's first-ever /recommendations call (necessarily a cache miss) reflects the tag right away.

Batch 11 — Notifications

Doesn't trigger new actions — every one of the 12 notification types was already triggered as a side effect of Batches 2 through 8 (invite, accept, cancel, pin propose/change/confirm, hangout completion, activity approve/reject, comment approve/reject, badge earned). This batch confirms each one landed as a real row, for the right recipient, by reading it back from GET /notifications — polling briefly, since Kafka delivery is asynchronous — then checks POST /notifications/:id/read marks one row read without touching anyone else's.
